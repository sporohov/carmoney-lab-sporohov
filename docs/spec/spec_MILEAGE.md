# Spec MILEAGE: учёт пробега в решении по заявке

Спецификация по docs/intent/intent_MILEAGE.md. Каждое требование атомарно и
проверяемо; у каждого критерия приёмки и каждого числа указан источник.
Требований сверх intent нет — соответствие проверяется по разделу 5.

## 1. Контекст

Решение по заявке сегодня считается только по LTV: `LTV < 60.0 → approve`,
`60.0…85.0 → review`, `> 85.0 → reject` (backend/config/rules.php:44–45,
backend/src/Domain/DecisionEngine.php:32–40). Пробег в решении не участвует —
он только валидируется на входе в диапазоне 0…500 000 км
(backend/src/Domain/ApplicationValidator.php:43–46, rules.php:23); заявки с
пробегом больше 500 000 км до решения не доходят, ошибки валидации
возвращаются HTTP-слоем с кодом 422 (backend/src/Http/ApplicationController.php:30,61).
Если поле `mileage` не пришло, валидатор подставляет `-1` и заявка падает
с ошибкой валидации (ApplicationValidator.php:43).

Известное расхождение кода и докблока `DecisionEngine` на границе 60.0
(строгая проверка `<` вместо `<=`) — вне задачи (intent §3).

## 2. Входит / не входит

**Входит:**

- правило учёта пробега в расчёте решения по заявке: REQ-MILEAGE-01…03;
- фиксация текущего поведения заявки без поля пробега: REQ-MILEAGE-04;
- порог 400 000 в справочнике `backend/config/rules.php` — бизнес-числа
  в коде не хардкодятся (конвенция репозитория, AGENTS.md §4);
- тесты: юнит-уровень `DecisionEngine` и интеграционный сценарий
  «валидация → LTV → пробег → решение» через `AssessmentService::assess()`.

**Не входит** (intent §5, ответ заказчика «как в плане»):

- проверка входных данных и её предел 500 000 км (`max_mileage_km`),
  включая тексты сообщений валидатора;
- пороги решения по LTV 60.0 / 85.0 и существующее расхождение кода и
  описания на границе 60.0;
- фронтенд;
- база данных и миграции;
- задача LOAN-12 — лимит по возрасту авто (`ltv_by_age`).

## 3. Требования и критерии приёмки

### REQ-MILEAGE-01. Понижение approve до review при пробеге больше 400 000 км

В расчёте решения по заявке пробег больше 400 000 км делает решение
`approve` невозможным: оно понижается до `review`. Пробег ровно 400 000 км —
граница включительная, понижения нет.

- AC-MILEAGE-01: валидная заявка с LTV в зоне approve (тестовое значение
  50.0) и пробегом **399 999** км → `decision = approve`.
- AC-MILEAGE-02: та же заявка с пробегом **400 000** км → `decision = approve`.
- AC-MILEAGE-03: та же заявка с пробегом **400 001** км →
  `decision = review`, `approved_limit = 0` (лимит привязан к решению —
  текущее поведение, AssessmentService.php:39).

### REQ-MILEAGE-02. Правило живёт в решении, а не в валидации

Заявка с пробегом 400 001…500 000 км остаётся валидной и доходит до расчёта
решения. Диапазон валидации 0…500 000 км не меняется.

- AC-MILEAGE-04: заявка с пробегом 400 001 (любое значение ≤ 500 000)
  проходит валидацию и получает ответ с решением, а не ошибку валидации:
  `review` при LTV 50.0, HTTP 200 на `/api/ltv` (не 422).
- AC-MILEAGE-05: заявка с пробегом **500 001** км → ошибка валидации поля
  `mileage`, HTTP 422 — поведение валидатора не изменилось.

### REQ-MILEAGE-03. Приоритет перед решением по LTV

Высокий пробег не смягчает и не меняет `reject` и `review`: понижение
применяется только к `approve`.

- AC-MILEAGE-06: заявка с LTV в зоне reject (тестовое значение 95.0) и
  пробегом 400 001 км → `decision = reject` (не `review`).
- AC-MILEAGE-07: заявка с LTV в зоне review (тестовое значение 75.0) и
  пробегом 400 001 км → `decision = review`.

### REQ-MILEAGE-04. Заявка без поля пробега — поведение не меняется

Отсутствие поля `mileage` остаётся ошибкой валидации: заявка до расчёта
решения не доходит, правило пробега для неё не срабатывает.

- AC-MILEAGE-08: payload без поля `mileage` → `ValidationException` с
  ошибкой поля `mileage` (HTTP 422), решение не вычисляется.

| 399 999 / 400 001 | граничные значения AC | задание ДЗ.1 (красный тест на 399999/400000/400001); производные от порога 400 000 |

| −1 | дефолт отсутствующего `mileage` | ApplicationValidator.php:43 — текущий код |

## 6. Контекст для планирования (не требования)

Факты из кода, которые план обязан учесть (без них красная/зелёная фазы
споткнутся):

- существующий `tests/Unit/DecisionEngineTest.php` вызывает
  `decide($ltv)` с одним аргументом (строки 17, 23) — расширение сигнатуры
  `decide()` затронет существующий тест; по ДЗ тесты в фазе зелёного кода
  не трогаем, значит вопрос совместимости нужно решить в плане;
- каталог `tests/Feature/` не существует — интеграционные сценарии в ДЗ
  ложатся на `tests/Unit/AssessmentServiceTest.php` (фикстура
  `mileage = 96000`, LTV 50.0/75.0/95.0 — не ломать);
- существующие тесты НЕ покрывают: пробег за пределом 500 000, отсутствие
  поля `mileage` — оба кейса новые (AC-MILEAGE-05, AC-MILEAGE-08);
- `DecisionEngine` получает пороги через конструктор
  (DecisionEngine.php:24), `AppFactory::create()` передаёт только
  `rules['ltv']` (AppFactory.php:37) — место для прокидывания нового порога.
