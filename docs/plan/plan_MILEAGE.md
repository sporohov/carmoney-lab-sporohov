# План MILEAGE: пробег > 400 000 км → решение `review`

Статус: черновик, требует ответов на вопросы в конце (раздел 6).

## Контекст (из docs/setup/code_map.md и разведки @scout)

- Пробег сейчас участвует **только** в валидации: `ApplicationValidator` (строки 43–46)
  проверяет диапазон 0…`max_mileage_km` = 500 000 (`backend/config/rules.php:23`).
  При нарушении — `ValidationException`, заявка до решения не доходит.
- `DecisionEngine::decide(float $ltv)` принимает только LTV; пробег до него не
  доходит, хотя уже лежит в `$input['mileage']` внутри `AssessmentService::assess()`
  (строка 30, используется на 32–33).
- Конструктор `DecisionEngine` получает только `rules['ltv']` (`AppFactory.php:37`).
- Значит, новое правило — правило **решения**, а не валидации; фактически оно
  сработает только в диапазоне 400 000 < пробег <= 500 000 (больше 500 000
  отсекается валидацией).

Принятая семантика (уточнена вопросом Q1, Q2 в разделе 6): порог
`review_mileage_km = 400 000`; при `mileage > 400 000` решение не может быть
`approve` — оно понижается до `review`. `reject` по LTV остаётся `reject`
(пробег не «смягчает» отказ). Граница «не больше 400 000» — включительная:
400 000 проходит без понижения.

## 1. Файлы

  `review_mileage_km => 400000` с комментарием, что это порог решения
  (в отличие от валидационного `max_mileage_km`).
- `backend/src/Domain/DecisionEngine.php` — расширить сигнатуру
  `decide(float $ltv, int $mileage): string`, в конструкторе принять
  `review_mileage_km`, после LTV-веток добавить понижение `approve` → `review`
  при превышении порога; обновить докблок класса (правило про пробег + факт
  расхождения `<` vs `<=` не менять без отдельного решения).
- `backend/src/Domain/AssessmentService.php` — строка 33: передать
  `$input['mileage']` вторым аргументом в `decide()`.
- `backend/src/AppFactory.php` — строка 37: `new DecisionEngine($rules['ltv'])`
  заменить на передачу и `rules['vehicle']['review_mileage_km']` (вариант:
  передать весь `$rules['vehicle']`; см. шаг 2).

## 2. Шаги реализации

1. `rules.php`: добавить `review_mileage_km => 400000` рядом с `max_mileage_km`,
   прокомментировать различие порогов (валидация vs решение).
2. `DecisionEngine`: принять порог в конструкторе (расширить docblock-тип
   `$thresholds`), добавить в `decide()` аргумент `int $mileage`. Логика:
   вычислить LTV-решение как сейчас; если оно `APPROVE` и
   `$mileage > $this->reviewMileageKm` — вернуть `self::REVIEW`; иначе вернуть
   LTV-решение. Числа не хардкодить — только из конструктора.
3. `AssessmentService::assess()`: `decide($ltv, $input['mileage'])`.
4. `AppFactory`: прокинуть `rules['vehicle']['review_mileage_km']` в
   `DecisionEngine` (совместимо с `?array $rules` — при отсутствии ключа
   упадёт с понятной ошибкой; дефолт не изобретаем).
5. Тесты (раздел 3), прогон `make test`, `make lint`.
6. Обновить `docs/setup/code_map.md`: раздел «Гипотетическое правило» заменить
   на описание реализованного (порог, приоритет, диапазон действия
   400 000 < x <= 500 000).

## 3. Тесты

Юнит (`DecisionEngineTest`) — фиксировать LTV в зоне `approve` (например, 50):

- `decide_returns_approve_when_mileage_399999` — approve;
- `decide_returns_approve_when_mileage_400000` — граница включительна, approve;
- `decide_returns_review_when_mileage_400001` — понижение approve → review.

Интеграция (`AssessmentServiceTest`) — валидная заявка с низким LTV:

- `assess_returns_review_for_mileage_400001` — payload с mileage 400 001 и LTV < 60
  даёт `decision: review`, `approved_limit: 0`;
- `assess_keeps_reject_for_high_ltv_and_high_mileage` — LTV > 85 при любом пробеге
  остаётся reject (пробег не смягчает);
- `assess_returns_approve_for_mileage_400000` — граница.

Пустой пробег (поведение не меняем, фиксируем текущее):

- `assess_rejects_payload_without_mileage` — payload без `mileage` падает в
  `ValidationException` с ошибкой поля `mileage` (сейчас по умолчанию `-1`).
  Это тест-документация: пустой пробег — ошибка валидации, а не `review`.

## 4. Риски

- **`max_mileage_km` = 500 000 (валидация)** — пороги близки и их легко
  перепутать: если новое правило случайно вписать в валидатор, заявки с пробегом
  400 001+ начнут падать с 422 вместо `review`. Митигация: имя ключа
  `review_mileage_km`, комментарий в `rules.php`, тесты на оба порога.
- **Приоритет reject vs review** — коде нет механизма комбинирования правил;
  выбранная семантика «reject не понижается» — проектное решение, требует
  подтверждения (Q1).
- **Сигнатура `decide()`** — расширение аргументом ломает всех внешних
  вызывателей; в репозитории вызов один (`AssessmentService`), но скрытые
  вызовы из тестов/скриптов возможны — `make test` покажет.
- **Расхождение докблоков и кода** по границе `<=`/`<` в `DecisionEngine`
  (code_map, строки 41–43) — при правке легко «заодно» поменять семантику
  LTV-границы и сломать существующие решения. Не трогаем в этой задаче.
- **`AppFactory` с `?array $rules`** — тесты/моки, передающие урезанный
  `$rules` без нового ключа, упадут; потребуется фиксure-обновление.
- **Не входит**: правки `max_mileage_km`, повышающие коэффициенты по возрасту,
  лимит по `ltv_by_age` (LOAN-12), изменения фронта (`frontend/` не трогаем —
  поле уже есть), миграции БД (`mileage_km` уже INT UNSIGNED), правка сообщений
  валидатора.

## 5. Чего не хватает / что не входит

- Не хватает подтверждения приоритета правил (см. Q1) и судьбы пустого
  пробега (Q3). Остальное покрывается разведкой scout и code_map.
- Вне задачи: любое изменение LTV-порогов, валидационного `max_mileage_km`,
  фронтенда и БД.
